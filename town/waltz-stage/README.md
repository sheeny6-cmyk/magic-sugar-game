# 3/4 왈츠 · 세 박의 발레 (왈츠 스테이지 시제품)

`town/first-dance/`를 다시 설계한 왈츠 리듬 스테이지입니다. 기존 경로(`first-dance`, `studio`, `stage`, `sugar-works`)와
저장 기록(`localStorage`)은 건드리지 않습니다.

- 플레이: `https://sheeny6-cmyk.github.io/magic-sugar-game/town/waltz-stage/`
- 조작: 화면 아래 4버튼(🐈 파드샤 · 🦋 그랑제떼 · ═ 아라베스크 · ↻ 피루엣), PC에서는 키 `1~4`
- 한 판 약 54초 · 34개의 박 · 마을 기록에 영향 없음

## 1. `town/first-dance/` 구조 분석 (왜 다시 만들었나)

| # | 문제 | 근거 |
| --- | --- | --- |
| 1 | **두 개의 시계** | 화면·판정은 `begin = performance.now()` 기준, 음악은 `SugarMusic.start()`가 호출된 순간의 `AudioContext.currentTime` 기준. `startSong()`이 `await resume()` 뒤에 실행되므로 두 시계의 출발점이 다르다. 실측: 같은 순간에 화면 시계가 **약 83~96ms 앞서** 있었다(390×844, 첫 박에서 역산). PERFECT 판정 폭 ±175ms의 절반을 여기서 잃는다. |
| 2 | **등간격 패턴** | `beats = [3,6,9,…,42]` — 3박마다 정확히 **1,875ms 간격 14개**. 왈츠의 강-약-약도, 선율의 프레이즈도 반영되지 않아 모든 노트가 같은 무게로 보인다. |
| 3 | **공통 타임라인 없음** | 연습이 끝나면 `beginShow()`가 `setTimeout(i*1220)`로 공연 장면을 다시 돌리고, 음악은 0초부터 재생한다. 화면의 동작 타이밍과 음악의 마디가 서로 무관하다. |
| 4 | **정답이면 장애물이 사라짐** | 성공 시 `.event.resolved{opacity:.65}` — 장애물이 흐려질 뿐 지나가지 않는다. 슈가는 `dance()`의 CSS 키프레임(`catDance`/`jumpDance`)이 **누른 순간** 시작되므로, 일찍 누르면 장애물이 오기 전에 점프가 끝나 발밑으로 장애물이 지나간다. |
| 5 | 정지 이미지 + 즉시 교체 | `setImage()`가 `<img src>`를 갈아 끼워 포즈가 툭툭 끊긴다. 예비·도약·착지의 중간 자세가 없고, 잔상·발끝 빛도 없다. |
| 6 | 화면 높이 | 390×844에서 문서 높이 **872px**(28px 스크롤). 월드가 47dvh를 차지해 버튼과 안내가 아래로 밀린다. |

## 2. 새 구조

### 단일 마스터 클록

```
t0 = 곡 0박이 울릴 AudioContext 시각        (music.js: start() 반환값)
songTime = ctx.currentTime - t0             (waltz.js: clock())
```

- 음악은 `start()`에서 **전곡을 한 번에 예약**한다(카운트인 3박 포함). 재생 중 타이머로 밀어 넣지 않으므로 드리프트가 없다.
- 노트 X좌표 `judgeX + (note.t - songTime) * SPEED`, 판정 시각, 슈가의 예비-도약-착지, 박자 표시, 스포트라이트, 바닥 스크롤 — **모두 같은 `songTime`을 읽는다.**
- `visibilitychange`에서 `ctx.suspend()`를 쓰므로 탭을 벗어나면 `currentTime`이 멈춰 화면과 음악이 함께 멈춘다(기존처럼 시계를 따로 보정하지 않는다).
- 오디오가 없는 브라우저에서는 같은 API의 `performance.now()` 대체 시계로 게임이 계속 돌아간다(음악만 없음).

### 곡과 차트 (96 BPM · 3/4 · 28마디 · 54.4초)

| 구간 | 마디 | 박 | 시간 | 음악 | 노트 |
| --- | --- | --- | --- | --- | --- |
| 카운트인 | — | -3~-1 | -1.9~0초 | 나무 소리 3박 | — |
| 도입 | 0~4 | 0~15 | 0~11.3초 | 뮤직박스 단선율 | 5.6초 🐈 / 9.4초 🦋 (1마디 이상 간격) |
| 전개 | 5~15 | 15~48 | 11.3~31.9초 | 왈츠 반주(베이스+2·3박 화음)+선율 | 강박 도약 + 약박 스텝, 20.6~22.5초 균형대 3연속 |
| 절정 | 16~27 | 48~84 | 31.9~54.4초 | 옥타브 중복·아르페지오·확장 화음 | 피루엣 연속(48·51·54·57박) → 파드샤→그랑제떼→아라베스크→피루엣 연결(60~63박) → 720° 피루엣 → 르베랑스 |

- 모든 노트는 **선율의 음이 떨어지는 박**에 놓았다(`music.js`의 `MEL` 표와 `waltz.js`의 `CHART`가 같은 박을 쓴다).
- 판정 폭: PERFECT ±115ms, GOOD ±245ms(1박 625ms).

### 장애물을 넘어가는 동작

| 노트 | 장애물 | 슈가의 동작 (모두 `songTime`의 함수) |
| --- | --- | --- |
| 파드샤 | 고양이(벡터) | -0.46초 플리에 → 포물선 62px 도약(아라베스크 자세 + 잔상 3장) → 플리에 착지 |
| 그랑제떼 | 허들(벡터) | -0.52초 깊은 플리에 → 108px 도약, 11° 기울기, 잔상 4장 → 착지 |
| 아라베스크 | 균형대(벡터) | 34px 올라서 아라베스크로 균형(미세 흔들림) → 균형대가 발밑을 지나간 뒤 내려섬 |
| 피루엣 | 회전 존(빛의 원) | 를르베 → `cos` 눌림 회전(1바퀴 또는 2바퀴) + 잔상 6장 + 허리 높이 회전 호 + 발끝 빛 + 반짝임 → 플리에 착지 |

- 성공해도 장애물은 **사라지지 않는다.** 계속 왼쪽으로 흘러가고, 판정선을 지나는 순간 반짝임만 남긴다.
- 실패하면 슈가가 휘청이고 장애물은 붉은 빛을 남긴 채 그대로 지나간다.
- 정지 이미지로 불가능한 부분(접힌 다리·180° 벌림·등 모습)은 `SPRITE_REQUIREMENTS.md`에 프레임 단위로 적었다.

## 3. 검증 (`tmp/waltz_final.py` · 로컬 http 서버 + Playwright, 라이브 URL 동일 스크립트)

라이브 `https://sheeny6-cmyk.github.io/magic-sugar-game/town/waltz-stage/` · 390×844 · iPhone 계열 UA 없음(모바일 뷰포트 + 터치):

| 항목 | 결과 |
| --- | --- |
| 레이아웃 | `scrollHeight 844 = clientHeight 844`, `scrollWidth 390 = clientWidth 390`, 가로 넘침 0건 |
| 플레이 | 실제 버튼에 `pointerdown`을 보내 34개 노트 완주 → **34/34 PERFECT**, 판정 오차 -8~-24ms(테스트가 의도한 -25ms 리드) |
| 결과 | 랭크 **S**, 정확도 100%, 파드샤 11/11 · 그랑제떼 8/8 · 아라베스크 6/6 · 피루엣 9/9 |
| 콘솔/페이지 오류 | **0건** |
| 오디오 | `AudioContext.state = running`, `baseLatency 0.01` |
| 소리↔시계 | `__waltz.meter()`(AnalyserNode)로 카운트인 3클릭을 재면 -1.853 / -1.235 / -0.613초에 검출 — 예약 -1.875 / -1.25 / -0.625초와 **+12~22ms** 차이. 이 편향은 분석 창(1024샘플 ≈23ms)과 rAF 샘플링(16ms)에 해당하며 세 클릭이 같은 값을 보여 **오디오가 박 격자에 정확히 놓였음**을 보인다 |

같은 스크립트를 360×640에서도 돌려 `scrollHeight 640 = clientHeight 640`, 넘침 0건을 확인했다.

> 이 검증에서 카운트인 3박이 곡 시작과 *동시에* 울리는 버그를 찾아 고쳤다(`music.js`: `tOf(-3+i)` → `(i-LEAD)*BEAT`). 고치기 전에는 첫 1.9초가 무음이었다.

### 남은 한계 (정직한 구분)

- **되는 것**: 음악 박자·노트 이동·판정·도약 궤적·착지·박자 표시가 모두 한 시계로 맞는다. 장애물은 사라지지 않고 발밑을 지나간다. 720° 피루엣·화음 확장·아르페지오까지 곡이 코스 길이에 맞게 구성되어 있다.
- **안 되는 것**: 정지 이미지 6장으로는 접힌 다리(파드샤 정점)·180° 벌림(그랑제떼)·등 모습(피루엣)을 만들 수 없다. 지금은 자세 변형과 잔상으로 흉내만 낸다. 필요한 프레임은 `SPRITE_REQUIREMENTS.md`에 적었다.
- **모바일 실기기**: 검증은 Chromium 모바일 에뮬레이션(390×844, 터치)이다. 실제 안드로이드 Chrome에서의 오디오 잠금 해제·발열은 이 시제품에서 아직 재지 않았다.
